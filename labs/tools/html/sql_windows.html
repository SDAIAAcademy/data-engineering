1 · GROUP BY collapses rows, OVER keeps them¶

GROUP BY customer_id turns each group of rows into one row.

🔍 Eight rows. A window function computes an aggregate over the rows related to the current row (its window) and writes the answer next to the row instead of replacing the group with it. PARTITION BY customer_id says "the window of a row is every row with the same customer". So you can compare a row to its group without a self-join.

2 · PARTITION BY and ORDER BY: each row's window¶

OVER () with nothing inside: the window is the whole table. PARTITION BY cuts it into groups.

🤔 Predict · Below, the only difference between total and with_order is ORDER BY created_at inside OVER. Will with_order be the same as total? If not, what will it be for customer 101?

In [9]:
con.sql("""
    SELECT order_id, customer_id, created_at, amount,
           sum(amount) OVER ()                                              AS everything,
           sum(amount) OVER (PARTITION BY customer_id)                      AS total,
           sum(amount) OVER (PARTITION BY customer_id ORDER BY created_at)  AS with_order
    FROM orders ORDER BY customer_id, created_at
""").df()
Out[9]:

🔍 Adding ORDER BY turned the total into a running total (40, 100, 120 for customer 101). With an ORDER BY, the default window of a row is no longer the whole partition but "from the start of the partition up to this row". This catches everyone once; §5 shows how to say exactly which rows you want (the frame).

The ORDER BY inside OVER defines each row's window; the one at the end only sorts the output. They don't have to match.

3 · Ranking: ROW_NUMBER, RANK, ties, deduplication¶

Ranking functions take no argument: they number the rows of each partition in the ORDER BY of the window.

🤔 Predict · Customer 101 has two events with lsn 22 (the redelivery). Ordered by lsn DESC, what do row_number, rank and dense_rank give those two rows, and the next one?

In [11]:
con.sql("""
    SELECT customer_id, lsn, arrival, op, city,
           row_number() OVER w AS row_number,
           rank()       OVER w AS rank,
           dense_rank() OVER w AS dense_rank
    FROM changes
    WINDOW w AS (PARTITION BY customer_id ORDER BY lsn DESC)
    ORDER BY customer_id, lsn DESC
""").df()
Out[11]:
customer_id lsn arrival op city row_number rank dense_rank
0 101 22 5 u Jeddah 1 1 1
1 101 22 6 u Jeddah 2 1 1
2 101 18 7 u Riyadh 3 3 2
3 101 15 3 u Dammam 4 4 3
4 101 10 1 c Riyadh 5 5 4
5 102 17 4 u Riyadh 1 1 1
6 102 12 2 c Jeddah 2 2 2
7 103 30 9 d NaN 1 1 1
8 103 25 8 c Dammam 2 2 2

🔍 row_number always gives 1, 2, 3...: on a tie it breaks it arbitrarily, so which copy gets 1 can change from run to run. rank gives ties the same number and skips (1, 1, 3); dense_rank doesn't skip (1, 1, 2). WINDOW w AS (...) names a window so several functions can share it.

Harmless here, because the two copies are identical. When tied rows differ, "the latest row" is a coin flip: add a tie-breaker to the ORDER BY (lsn DESC, arrival DESC), or deduplicate first.

Deduplication is itself a ranking problem: number the copies of each lsn and keep copy 1. Filtering on a window result needs a subquery here (§6 shows a shortcut). The rest of the walkthrough reads this dedup view:

In [12]:
con.sql("""
    CREATE OR REPLACE VIEW dedup AS
    SELECT * EXCLUDE (copy) FROM (
        SELECT *, row_number() OVER (PARTITION BY lsn ORDER BY arrival) AS copy FROM changes
    ) WHERE copy = 1
""")
print(con.sql("SELECT count(*) FROM changes").fetchall()[0][0], "events ->", con.sql("SELECT count(*) FROM dedup").fetchall()[0][0], "after dedup")

9 events -> 8 after dedup

The same pattern gives each customer's last change: number their rows from the highest lsn down, keep number 1.

4 · LAG and LEAD: looking at the neighbours¶

lag(x) reads x from the previous row of the window, lead(x) from the next one. At the edges of a partition there is no neighbour, so you get NULL (or a default: lag(x, 1, 'none')).

🤔 Predict · For customer 102 (two events), what are prev_city and next_lsn on each row?

In [15]:
con.sql("""
    SELECT customer_id, lsn, op, city,
           lag(city) OVER w  AS prev_city,
           lead(lsn) OVER w  AS next_lsn
    FROM dedup
    WINDOW w AS (PARTITION BY customer_id ORDER BY lsn)
    ORDER BY customer_id, lsn
""").df()

5 · Frames: "everything before me"¶

The frame says which rows of the partition an aggregate sees, relative to the current row: ROWS BETWEEN <start> AND <end>, where each end is UNBOUNDED PRECEDING, n PRECEDING, CURRENT ROW, n FOLLOWING or UNBOUNDED FOLLOWING. (Ranking functions and lag/lead ignore frames.)

To see a frame, aggregate with list(order_id): it collects the ids of exactly the rows sum or max would see with the same OVER (...).

🤔 Predict · Orders 6 and 7 share a date. Which ids will each column list on order 6's row?

In [18]:
frames = con.sql("""
    SELECT order_id, created_at, amount,
           list(order_id) OVER (ORDER BY created_at, order_id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS rows_running,
           list(order_id) OVER (ORDER BY created_at)                                                            AS default_frame,
           list(order_id) OVER (ORDER BY created_at, order_id ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING) AS before_me,
           list(order_id) OVER (ORDER BY created_at, order_id ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING)         AS neighbours
    FROM orders ORDER BY created_at, order_id

🔍 The default frame with an ORDER BY is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, and RANGE includes the current row's peers (rows with the same ORDER BY value). So order 6's default frame already contains order 7, and a "running total" by date jumps by both orders at once. When you mean rows, write ROWS and give the ORDER BY a tie-breaker.

before_me finds the events that arrived out of order: their lsn is smaller than the largest lsn among everything that arrived before them.

6 · Evaluation order: why WHERE can't, and QUALIFY can¶

§3 needed a subquery to keep rn = 1. Why not just WHERE row_number() OVER (...) = 1?

In [21]:
try:
    con.sql("SELECT * FROM dedup WHERE row_number() OVER (PARTITION BY customer_id ORDER BY lsn DESC) = 1").df()
except duckdb.Error as e:
    print(type(e).__name__, "→", str(e).splitlines()[0])

BinderException → Binder Error: WHERE clause cannot contain window functions!

🔍 A SELECT is evaluated, logically, in this order: FROM → WHERE → GROUP BY → HAVING → window functions → QUALIFY → SELECT / DISTINCT → ORDER BY → LIMIT. WHERE runs before any window exists, so it can't use one. QUALIFY (DuckDB, Snowflake, BigQuery, Databricks; not PostgreSQL) is a WHERE that runs after the windows. (The optimizer may execute in another order, but the result is always as if it followed this one.)

§3's "last change per customer", without the subquery:

In [22]:
latest_q = con.sql("""
    SELECT customer_id, lsn, op, city
    FROM dedup
    QUALIFY row_number() OVER (PARTITION BY customer_id ORDER BY lsn DESC) = 1
    ORDER BY customer_id
""").df()
U.check(latest_q.equals(latest), "same result as the subquery version")

✅ same result as the subquery version

The order matters for more than syntax. We want the periods without the delete rows, and filtering them with WHERE or with QUALIFY looks interchangeable.

🤔 Predict · In which of the two queries below is customer 103 (deleted on 20 September) still current (valid_to is NULL)?

In [23]:
too_early = con.sql("""
    SELECT customer_id, city, changed_at AS valid_from,
           lead(changed_at) OVER (PARTITION BY customer_id ORDER BY lsn) AS valid_to
    FROM dedup WHERE op <> 'd'                       -- filter BEFORE the window
    ORDER BY customer_id, valid_from
""").df()
after = con.sql("""
    SELECT customer_id, city, changed_at AS valid_from,
           lead(changed_at) OVER (PARTITION BY customer_id ORDER BY lsn) AS valid_to
    FROM dedup QUALIFY op <> 'd'                     -- filter AFTER the window
    ORDER BY customer_id, valid_from
""").df()
pd.concat({"WHERE (too early)": too_early[too_early.customer_id == 103],
           "QUALIFY (after)": after[after.customer_id == 103]})
Out[23]:

WHERE (too early) 6 103 Dammam 2026-09-14 11:00:00 NaT
QUALIFY (after) 6 103 Dammam 2026-09-14 11:00:00 2026-09-20 15:00:00

🔍 With WHERE, the delete is gone before lead runs, so customer 103 looks like they still live in Dammam today. With QUALIFY, lead sees the delete, closes the period on 20 September, and only then is the delete row removed. Same filter, different place in the evaluation order, different history.

def as_tuples(df):
    """The history as a list of (customer_id, city, valid_from, valid_to) tuples, to compare with `expected`."""

def history_variant(source="changes", order_by="lsn", dedup=True):
    rows = f"(FROM {source} QUALIFY row_number() OVER (PARTITION BY lsn ORDER BY arrival) = 1)" if dedup else source
    return con.sql(f"""
        SELECT customer_id, city, changed_at AS valid_from, lead(changed_at) OVER w AS valid_to
        FROM {rows}
        WINDOW w AS (PARTITION BY customer_id ORDER BY {order_by})
        QUALIFY op <> 'd'
        ORDER BY customer_id, valid_from
    """).df()

9 · Summary¶












It does
an aggregate or a neighbour's value next to every row, without collapsing rows or a self-join · rank, dedupe and keep the latest per key · running totals and "everything before me"




It doesn't
filter in WHERE (windows run after it: use QUALIFY or a subquery) · break ties for you (row_number on a tie is arbitrary) · see other partitions




In this course
Lab 1.3 practises them · dedup, latest state and city history (SCD Type 2) from the customer edits (Lab 2.3)




In other engines
the same OVER (...) in PostgreSQL, Snowflake, BigQuery, Spark SQL and Databricks; QUALIFY everywhere except PostgreSQL






Cheat sheet






Code
Does






f(x) OVER (PARTITION BY k)
the group's answer on every row of the group




... OVER (PARTITION BY k ORDER BY t)
a running answer: from the start of the partition up to the row (and its peers)




row_number(), rank(), dense_rank()
1, 2, 3 · 1, 1, 3 · 1, 1, 2 on a tie




QUALIFY row_number() OVER (PARTITION BY k ORDER BY t DESC) = 1
the latest row per key; PARTITION BY id keeps one copy per id




lag(x), lead(x), lag(x, 1, default)
the previous / next row's value, NULL at the edges




lead(changed_at) OVER (PARTITION BY k ORDER BY lsn)
when a period ends: its valid_to




ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING
everything before me




ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING
my neighbours and me




WINDOW w AS (...), then OVER w
one window shared by several functions
