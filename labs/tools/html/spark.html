0 · The problem: do you need a cluster?¶

Scale up first; scale out when you must. DuckDB and Polars handle hundreds of gigabytes on one large VM, with no cluster to run. A cluster earns its cost when:

  • a single job reads terabytes, more than one machine can scan in the time you have;
  • the work must finish inside a window (say 01:00 to 05:00) that one machine can't meet;
  • many teams share one platform, its data and its compute.

You will meet Spark anyway: the big cloud platforms run it, and many existing pipelines are written in it. Our data fits on a laptop many times over; we run Spark on it to see how a cluster splits the work.

1 · Why Spark: one driver, many executors¶

Spark splits the data into pieces and sends the work to many machines. The driver plans the work, the executors do it, and each executor core works on one piece at a time. Start Spark first (on Colab this installs Java), then step through the picture.

The problem. Say Qafila keeps 2 TB of order lines. One core reads Parquet at roughly 200 MB/s, so a single pass takes about 10,000 seconds: almost 3 hours. Next year there is more data, and the machine is the same size.

The words you'll read in the UI and in every Spark error message:

Word Is
driver your program: builds and optimizes the plan, schedules the tasks
cluster manager hands out machines: YARN, Kubernetes, standalone, or a managed service
executor a JVM process on a worker machine; runs tasks on its cores, can cache data
job the work one action starts (count, show, write, collect)
stage a run of work with no shuffle; each shuffle starts a new stage
task one stage on one partition; tasks run in parallel on executor cores

🔍 Here driver and executors share one process (local[2]). The code is the same on a 1,000-node cluster; only the master changes.

The Spark UI shows each job's stages and tasks, with time and rows per task: it's where you debug real jobs. Open it now and refresh it after each action below.

2 · Partitions are tasks¶

Spark splits every dataset into partitions. One partition processed on one core is one task. Input files are cut into splits of at most spark.sql.files.maxPartitionBytes (128 MB by default). Our order_items file is only 1.5 MB, so we lower the limit to 256 KB to see several tasks on a laptop.

🤔 Predict · With 2 cores, how many partitions should we hope for: 1, 2, or more?

🔍 With 2 cores, two tasks run at a time; on a cluster with 400 cores, 400 do. So we want more partitions than cores, so every core stays busy, but not millions of tiny ones, because each task has a fixed start-up cost. A bigger split size gives fewer, longer tasks.

3 · Lazy evaluation: transformations plan, actions run¶

Transformations (filter, withColumn, select, join, groupBy) don't run anything: they add a step to a plan. Only an action (count, show, collect, write) runs the plan as one or more jobs.

🤔 Predict · We filter, compute and select. How many Spark jobs does that run? And the count() after it?

4 · Narrow vs. wide: the shuffle¶

A narrow step needs only the rows in its own partition. A wide step needs rows from other partitions, so Spark has to shuffle: send every row, over the network, to the task that owns its key.

🤔 Predict · Purchasing wants units sold per product. Can each task answer that alone?

🔍 No. Lines for one product sit in every partition, so the plan has an Exchange hashpartitioning(product_id, 8). Notice the two HashAggregate steps: partial_sum runs before the shuffle, sum after. The 8 is spark.sql.shuffle.partitions (default 200; we set 8 for a laptop). distinct() is wide for the same reason, with the same two steps around an Exchange.

What does a shuffle actually move? Spark sends each key to bucket pmod(hash(key), 8), and F.hash is the same hash function, so we can compute where every row goes:

In [15]:
moves = (big_baskets
         .select(F.spark_partition_id().alias("map_task"),
                 F.pmod(F.hash("product_id"), F.lit(8)).alias("reducer"), "product_id")
         .groupBy("map_task", "reducer", "product_id").count()
         .toPandas())
V.shuffle(moves, key="product_id", n_out=8)

5 · Joins: broadcast vs. sort-merge¶

For a join, matching rows must meet in the same task. Either the small table is copied to every executor (broadcast), or both tables are shuffled by the join key (sort-merge).

Each order line needs its product's category: 170k rows against 356. Spark estimates products is tiny, so it broadcasts it.

6 · Skew: one key, one huge task¶

A shuffle puts all rows of a key in one task. If one key is much bigger than the others, one task gets most of the work, and the stage waits for it.

Operations wants orders per city. Qafila has 12 stores in 3 cities, and Riyadh is by far the biggest. We partition the orders by city into 8 partitions.

🤔 Predict · How many of the 8 tasks get work? Are they equal?

In [22]:

by_city = orders_city.repartition(8, "city")
skewed = (by_city.groupBy(F.spark_partition_id().alias("partition"), "city").count()
                 .orderBy("partition").toPandas())

🔍 Three keys can keep at most three tasks busy. Here it's worse: Jeddah and Riyadh hash to the same partition, so one task holds most of the orders while six tasks get nothing. The job finishes when that task finishes, and more executors don't help: one partition is still one task.

Fixes: AQE (on by default) splits oversized partitions in sort-merge joins at run time; salting spreads one key over several tasks; or pick a better key. Lab 3.2 measures skew on National Day and salts it.

7 · Writing: one file per task¶

Executors write in parallel, so every task writes its own file. The number of files is the number of tasks in the last stage, not something you choose directly. Here we spread big_baskets over 6 partitions before writing.

8 · Summary¶
It does DataFrame and SQL transformations over many machines · reads and writes Parquet, Iceberg and Delta tables · batch and streaming (Structured Streaming) · Python, SQL, Scala and Java on one engine
It doesn't pay off on data one machine handles (start-up, shuffles and a cluster to run) · store tables itself (a table format does: df.writeTo("cat.db.orders").append()) · schedule its jobs (Dagster, Day 4)
In this course Lab 3.2: one metric three ways, partition pruning, broadcast timing, salting, small files
As a service Databricks, AWS EMR and Glue, Google Dataproc, Microsoft Fabric, Azure Synapse: Spark with the cluster run for you

Cheat sheet

Code Means
spark.read.parquet(path) a DataFrame over Parquet files or a folder of them
filter, withColumn, select / groupBy, distinct, join narrow (no data moves) / wide (a shuffle, a new stage)
count, show, collect, toPandas, write actions: run the plan as jobs
df.explain() the physical plan; read it bottom-up; Exchange = a shuffle
df.rdd.getNumPartitions(), F.spark_partition_id() how many partitions / which one a row is in
spark.sql.files.maxPartitionBytes the input split size: bigger splits, fewer tasks
spark.sql.shuffle.partitions the number of partitions after a shuffle (default 200)
F.broadcast(df), df.hint("merge") force a broadcast join / a sort-merge join
df.repartition(n, "col") shuffle into n partitions by a key
df.write.partitionBy("col").parquet(path) one folder per value; one file per task per folder
spark.sql.adaptive.enabled AQE: merges small shuffle partitions and splits skewed join partitions at run time
