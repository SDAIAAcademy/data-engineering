The job

A data engineer gets data to the people who decide

From the systems that run the business to tested tables anyone can query. This is the platform you build this week.

This map is the whole week, left to right: sources, ingest (copy the data in), store, transform, test, serve. Below them, the three things that keep a platform alive: orchestrate, observe, govern. Do not explain the tools yet; each one gets its own session. A data engineer's day in one line: keep this path running, correct and on time, so analysts and data scientists never have to think about it. Pipeline: the code that moves and reshapes the data along this path.

Takeaway. Extract, load, transform: the raw rows stay as evidence, and every table can be rebuilt from them.
ETL is the older order: extract, transform, load, with the work done before the destination. The engine

DuckDB: an OLAP database in a library

No server: it runs inside your Python process, like SQLite. A column store, and it reads CSV, JSON and Parquet files directly.

DuckDB is the SQL engine in every lab this week. Snowflake, BigQuery and Redshift do the same columnar SQL at company scale, and what you learn here carries over. What it does not do: serve an app with many small writes, or let several processes write one file at once.

The shape of a question

Join on keys, filter, group: revenue by city

SELECT s.city,
       count(DISTINCT o.order_id) AS orders,
       round(sum(i.quantity * i.unit_price - i.discount), 2) AS revenue
FROM app.orders o
JOIN app.stores s      USING (store_id)
JOIN app.order_items i USING (order_id)
WHERE o.status = 'delivered'
GROUP BY ALL ORDER BY revenue DESC;

Takeaway. Why count(DISTINCT)? After the join there is one row per order line. count(*) would count lines and call them orders.
You know this SQL already; the point is the shape, which most analytical questions share. Revenue is not stored anywhere: it is quantity times unit price minus discount, on delivered orders. GROUP BY ALL is a DuckDB shortcut: group by everything not aggregated. Total: 40,419 delivered orders, 6,494,683.83 SAR. Delivery fees are excluded; Day 3 argues about that definition.

QUALIFY

WHERE can’t filter a window. QUALIFY can.

CREATE VIEW courier_clean AS
SELECT * FROM courier
QUALIFY row_number() OVER (
    PARTITION BY event_id ORDER BY ingest_time
) = 1;
22,518
events received
22,206
after removing 312 repeats
Why. SQL runs WHERE before any window exists, and QUALIFY after them. It works in DuckDB, Snowflake, BigQuery and Databricks. In PostgreSQL, use a subquery.
Run this one live if you have a moment: WHERE row_number() OVER (...) = 1 gives a binder error. The logical order is FROM, WHERE, GROUP BY, HAVING, window functions, QUALIFY, SELECT, ORDER BY. Lab 1.3 step 3 has this as an exercise with two blanks. 312 repeats match the issue log from Lab 1.1.

Folders by date: skip before opening a file

Lab 1.4 step 4 writes one folder per day. The date sits in the folder name, not in the file.

lake/lines/
  order_date=2026-08-01/data_0.parquet

  …
  order_date=2026-09-30/data_0.parquet
Why, if sorting already skips?
No other file is even opened, and a day’s load can replace one folder.
WHERE order_date = '2026-09-23'
1 of 61 filesopened, before any footer is read
WHERE created_at on the same day
61 of 61 filesopened: the engine can’t tell which folder holds the day
Takeaway. Partition: a folder per value. Engines skip folders only when you filter on the partition column itself.
order_date is created_at cast to a date, and it lives in the path. This is Hive-style partitioning. Filter on order_date and the engine opens 1 file; ask for the same day through created_at and it opens all 61 (the lab's stretch proves it). Dashboards often filter on the timestamp and lose the benefit. The folder also lets a daily load replace one day cleanly.

Takeaway. Partition by what you load and filter by, usually a date. Keep files large; sort for the rest.
Each small square is one real file. 732 files of about 43 kB: the work per file (list, open, read its statistics, schedule) outweighs the data, and on cloud storage each file is a paid request.
