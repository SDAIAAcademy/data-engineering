Three ways. Each one sees customer 100898’s evening differently.

Change data capture (CDC): learning every change a source makes. Reading its log is the complete way.
A build: one way per key press. Way 1, snapshot diff: copy the whole table every night and compare with yesterday’s copy. Fine for small tables, but it reads every row every time, and it sees only the net change per night: the 17:15 version, with the new email but the old city, never shows up. Way 2, query-based: WHERE updated_at > the last cursor. This is exactly what dlt’s incremental cursor did in D1_3. It is cheap and it works for many tables, but it misses hard deletes (the row is gone, so nothing matches), any change that doesn’t touch updated_at, and every version between two runs. A soft delete is different: the app keeps the row and sets is_deleted = 1, an ordinary update, so the cursor sees it (492 in September). Every consumer then has to filter those rows out. Way 3: log-based CDC reads the database’s own transaction log (PostgreSQL logical replication, the MySQL binlog). It sees both of 100898’s edits, deletes included, in commit order, and it doesn’t query the tables at all. The next slide shows what that log is.

MERGE updates, inserts and deletes by key, in one statement. DuckDB, Spark, Iceberg, Snowflake and BigQuery all run it.
The branches are checked top to bottom for each source row. Three versions, and exactly one is valid at any moment.
valid_to = lead(valid_from) OVER (PARTITION BY customer_id ORDER BY lsn)
Each version ends where the next begins: no gaps, no overlaps. Ordered by lsn, so arrival order can’t spoil it.
A build of Lab 1.4 task 4. Snapshot rows become the first versions, valid from their updated_at: 100898 signed up on 14 August 2025 and hadn’t changed since. valid_to null means current. Second press: lead() over lsn closes each version where the next begins, so out-of-order arrival doesn’t matter, and the duplicate was already dropped. A delete closes the last version and starts nothing.

11 / The words

Ten words for change and history

Every one appeared on a slide today. The lab uses them all.

  • CDC · learning every change a source makes
  • Log · where the database writes each change first
  • lsn · a change’s position in the log
  • Change event · one change: op, before, after, lsn
  • At-least-once · an event may arrive twice, or late
  • MERGE · update, insert or delete by key
  • Reconcile · prove the copy matches its source
  • Upsert · update the row if the key exists, insert it if not
  • SCD Type 2 · one row per version, valid_from to valid_to
  • As-of join · join to the version valid at the time
Order by lsn: most of the other words depend on it.
