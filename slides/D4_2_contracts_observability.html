02 / The contract

The contract as a file: ODCS

The Open Data Contract Standard (Bitol, Linux Foundation AI & Data): vendor-neutral YAML. An excerpt of Lab 4.2’s.

apiVersion: v3.1.0
kind: DataContract
id: urn:datacontract:qafila:payments-feed
version: 1.0.0
team:
  - {username: payments-provider-integration, role: owner}
support:
  - {channel: "#payments-data", tool: slack}
schema:
  - name: payments
    quality:
      - {metric: rowCount, mustBeGreaterThan: 1000}
    properties:
      - name: amount
        physicalType: DOUBLE
        required: true
slaProperties:
  - {property: latency, value: 1, unit: d}

apiVersion … version · which standard, which version

team · support · who owns it, where to ask

schema · tables, columns, types, rules

slaProperties · how fresh, how often

ODCS: schema, quality rules, service levels and people, in one file. v3.1.0 is the current release.
Lab 4.2’s contract, shortened. Four parts: metadata (the standard and the contract’s own version), people (team with roles, support channel: the social half of contracts), schema (every property with its logical and physical type, required, unique, classification and quality rules), and service levels (latency: the data is at most 1 day old; frequency: daily). Quality rules use metrics such as rowCount, nullValues, invalidValues and duplicateValues, or a SQL query against {object}. ODCS v3.2 is in development; v3.1.0 is what the tools support today.

Sources: Open Data Contract Standard · ODCS data quality · ODCS service levels

03 / Validate

A contract nobody checks is documentation

Each line of the contract becomes one query on the feed. Lab 4.2’s validator writes them.

Contract lineQueryResult
payment_id: uniquecount(*) - count(DISTINCT payment_id)0 ✓
amount: requiredcount(*) WHERE amount IS NULL0 ✓
status: validValues [captured, failed, refunded]WHERE status NOT IN (…)0 ✓
card_last4: pattern ^[0-9]{4}$WHERE NOT regexp_full_match(card_last4, …)0 ✓
type: sql · amount <= 0 · mustBe: 0SELECT count(*) FROM {object} WHERE amount <= 016 ✗
Executable contract: every rule is a query with an expected result. Run it on every load.
Lab 4.2 task 2: validate() walks the contract and turns each line into a query: types against DESCRIBE, required into a null count, unique into a duplicate count, and each quality rule into its metric. The custom SQL rule replaces {object} with the table. Khalid’s row passes every rule; the feed as a whole doesn’t. In production the datacontract CLI does exactly this (datacontract test), against DuckDB, Snowflake, Databricks or a Kafka topic.

04 / Change

status gets a new value, chargeback. Breaking?

Finance’s revenue logic: CASE WHEN status = ‘refunded’ THEN 0 ELSE amount END. Finance says: “Our CASE knows three statuses.”

Predict first: what does the CASE do with a chargeback?

No: no column was added or removed
Yes: chargebacks would count as revenue, silently
Only if the type of status changes
Yes. The CASE only knows refunded, so every chargeback stays in revenue. Not A: “only structural changes break things” is a misconception; the meaning changed. Not C: the column is still a string, but the set of values widened. Code that handles every known value mishandles a new one, often without an error.
Allow 45 seconds. B is right: a chargeback is money taken back, but the CASE only zeroes refunded, so every chargeback stays in revenue. No query fails, which is what makes it dangerous. A is the common misconception (only structural changes break things). C confuses type with meaning: the column is still a string. Widening the set of allowed values is a breaking change; narrowing it is safe.
04 / Change

Three of the five changes break something

Lab 4.2’s diff_contracts finds them. The rule: could an existing query fail, or change its answer?

payments feed · v1.0.0 → v2.0.0
propertyproposed changebreaking?what it does to Qafila

card_last4string → integeryes3,728 values start with 0: ‘0522’ becomes 522

Breaking: removed or renamed, retyped, newly optional, more allowed values. Safe: added, now required, fewer values.
The lab’s three breaking changes, each with its real effect. card_last4 is text for a reason: 3,728 of the 41,785 payments have last four digits starting with 0, like pay_9040149’s 0522, and an integer drops the zero. A required field becoming optional (the reverse of wallet_provider here) would also break consumers that never expected nulls. Lab 4.2 checks diff_contracts against exactly these sets.

04 / Change

A breaking change is a new major version

Publish v2 next to v1, give consumers time to move, then retire v1.

v1.0.0
amount, three statuses
v2.0.0
amount_sar, chargeback
v1 servedconsumers run on it
→
migration windowv1 and v2 served together
→
v1 retiredonly v2 served
diff_contracts in the provider’s CI: 3 breaking changes block the merge of v2 as a minor version.
Semantic versioning for data: breaking changes bump the major version and come with a migration window.
The same rule as for APIs. A minor version (1.1.0) may only add safe changes; anything breaking is 2.0.0 and is published beside 1.0.0, often as a second table or topic. Consumers migrate within an agreed window, then v1 is retired. Running the diff in the producer’s CI turns the rule into a merge check; datacontract changelog does it from two YAML files.

06 / Observability

Monitors watch what nobody promised

A contract checks what you expect. Five signals to watch on every important table, every day.

Freshnesswhen did it last change?
Volumedid the expected number of rows arrive?
Schemacolumns added, removed, retyped
Distributionnulls, ranges, the mix of values
Lineagewhat feeds it, who reads it
Today: freshness and volume, on the payments feed and the orders table.
+ cost: which models and queries burn the budget? Watch it like any metric.
Data observability: freshness, volume, schema, distribution and lineage, watched over time.
Tests and contracts are assertions you wrote down in advance. Monitors learn what normal looks like and flag deviations you didn’t think to test: a table that stopped updating, a day with half the rows, a column whose null rate jumped. Schema changes are the contract diff from the last chapter; lineage is the previous slide. Cost (FinOps) is the sixth signal many teams add: the most expensive model is often the least used.

07 / Volume

A naive monitor cries wolf every weekend

Expected = the median of the previous 7 days. Alert when a day is more than 20% off.

16
alerts in two months
14 of them are ordinary Thursdays and Fridays.
An alert that fires every week gets muted, and then it misses the real incident.
Lab 4.2’s naive monitor: 16 alerts, one red dot each. 14 are Thursdays and Fridays, which are always about 25% above the previous week’s median; the other two are National Day and the incident. After the second Thursday, the on-call engineer mutes the channel, and on 29 September nobody looks. A noisy monitor is worse than none: it teaches people to ignore alerts.

07 / Volume

Compare each day with the same weekday

Expected = the median of the same weekday over the previous 4 weeks. Alert at 30% off.

2
alerts in two months

Model the seasonality: weekdays, Ramadan, month-end. Then only the unusual days alert.
Lab 4.2’s smart monitor: for Tuesday 29 September the expected value is the median of the four previous Tuesdays, 720.5 orders; 308 is 57% below it. For National Day, the four previous Wednesdays give 704; 1,423 is 102% above. Two alerts in two months, both worth reading.
