02 / The rules

PDPL and NDMO, from a data engineer's seat

The Personal Data Protection Law: in force since September 2023, fully enforced since September 2024. SDAIA is the regulator.

PDPL covers lawful purpose, data minimization, data subjects' rights (access, correction, destruction), breach notification and conditions on transfers outside the Kingdom. Classification drives handling: the level decides who may read a column, and in what form.
The four NDMO levels are Top Secret, Secret, Restricted and Public. The national ID (and an IBAN, when present) is Secret; the name, email and mobile are Restricted; and every other column of a table that holds personal data is Restricted too, because combined with the rest it identifies someone. 03 / Discovery

A regex finds too much

Ten digits starting with 1 or 2 look like a national ID. So do the couriers' tracking numbers.

\b[12]\d{9}\b · in the 400 notes83 candidates
… that pass the Luhn check77 national IDs
… that don't6 tracking numbers
Check digit. A check digit tells a real ID from a random 10-digit number.
IBANs too. IBANs have one too: ISO 13616, mod 97.
A pattern finds candidates; a checksum confirms them. Fewer false alarms, more trust in the inventory.
Real counts from Lab 4.3: the regex finds every 10-digit number that starts with 1 or 2 in the notes, including 10-digit courier tracking numbers. Saudi national IDs and Iqama numbers end with a Luhn check digit, so the validator keeps only the real ones. The same idea confirms an IBAN: SA plus 22 characters, rearranged and taken mod 97, must give 1. Some personal data has no pattern at all (names, addresses): declare it in the catalog instead.

03 / Discovery

The Luhn check, on Khalid's ID

From the right: double every second digit, subtract 9 from results above 9, add everything up.

national_id1278681299
every 2nd from the right×2 = 2·×2 = 14·×2 = 12·×2 = 2·×2 = 18·
above 9: subtract 92258382299
First digit. 1 = a citizen, 2 = a resident (Iqama)
One wrong digit. Change any one digit and the total stops being a multiple of 10.
50
a multiple of 10 ✓
Luhn: a check digit that catches any single wrong digit and most swapped pairs.
Khalid's ID passes: 9 + 9 + 2 + 2 + 8 + 3 + 8 + 5 + 2 + 2 = 50. A random 10-digit number passes 1 time in 10.
A build-up: one press adds the last row and the sum. Khalid's ID is 1278681299; the first digit 1 marks a citizen (2 would be a resident's Iqama). From the right, the 2nd, 4th, 6th, 8th and 10th digits are doubled: 9, 1, 6, 7 and 1 become 18, 2, 12, 14 and 2. In the course data 4,612 accounts have a citizen's ID and 2,830 a resident's. Press once: above 9, subtract 9: 18 becomes 9, 12 becomes 3, 14 becomes 5. The sum of all ten results is 50, divisible by 10, so it is a well-formed ID. A tracking number such as 1234567890 sums to 43 and fails. Lab 4.3 task 1 writes is_saudi_id and is_saudi_iban; the detectors then use them as validators behind each regex.

05 / Pseudonymize

A plain hash re-identifies everyone

Lab 4.3's attacker holds 500 leaked national IDs and the "anonymous" hashed table.

58 people with two accounts: still found, from tokens alone. The key lives in a secret manager. Rotate it and every token changes.
Keyed hash (HMAC): a stable token per ID that nobody can recompute without the secret key.
Real results from Lab 4.3 task 3: with plain SHA-256 the attacker matches all 500 leaked IDs; with HMAC-SHA256 under a secret key, none. The tokens still find the 58 duplicate people. Khalid's HMAC token with the lab's default key starts 6fb6a0bd. Pseudonymized data is still personal data under PDPL: whoever holds the key can match it. It lowers the risk; true anonymization (aggregates, k-anonymity, differential privacy) is a much higher bar.

06 / Protect

A view is a convention. A policy is enforced.

Views work if every tool uses them. Warehouses attach the rule to the column itself.

CREATE VIEW analyst.customers AS
SELECT pseudo(national_id) AS person_token,
       customer_id, city, district,
       lower(split_part(email, '@', 2))
           AS email_domain,
       created_at
FROM main.customers;

Column masks and row filters

Snowflake, BigQuery, Unity Catalog: the rule applies in every tool

Tag-based policies

classify once (Secret); the mask follows the tag to every table

Roles, not people

grants go to support and analyst, and people join roles

Put the rule where the data is: a policy on the column or tag can't be bypassed by a new tool.
Lab 4.3's analyst view, as SQL. DuckDB has no column security, so the lab models it with views and a toy grant check. RBAC grants go to roles; people are added to roles.

07 / Erasure

Beyond the table: the rest of the checklist

Before you tell 100710 the data is gone, every copy from slide 4 needs an answer.

  • Derived tables · dbt rebuilds them; incremental models need a delete step
  • History · SCD2 versions (Lab 1.4 deletes them all)
  • Column statistics · min/max in old manifests can hold a value
  • Backups, replicas · expire them on a schedule you can name
  • Exports · files already sent to partners
  • Logs · keep the request, not the data
At scale. Batch erasures weekly, or crypto-shred: encrypt each person's data with their own key, and delete the key.
An erasure is a pipeline run: it must reach every layer, and leave a record that it did.
From the lab's closing notes. Old manifest files keep per-column lower and upper bounds, which for a single-row file are the value itself. dbt's table models drop the row on the next build; incremental models keep it unless a delete step runs. Doing all of this per request is expensive, so many teams batch erasures weekly within the legal deadline, or use crypto-shredding.
