Real rows from data/raw/qafila_oltp.sqlite (created_at 22:35:37 and updated_at 23:07:37 UTC). OLTP systems (the app’s SQLite here; PostgreSQL and MySQL in real apps) are built for many small transactions on current rows. OLAP systems are built for a few large reads over history. The next slide gives the questions their own place. How OLAP engines make big reads fast (storing by column) is the next session; how the tables are shaped for questions is Day 2.

Load first when the destination can do the work: the evidence stays, and every model can be rebuilt.
The picture is the same as the last slide; three reasons sit under the parts they belong to. One: loading becomes a plain copy, so one loader can serve every source and new sources arrive quickly. Two: the landed rows are the evidence. When a rule changes or a model has a bug, rerun the model; nothing has to be extracted again. That matters here because the app database keeps only each order’s current row (the status overwritten on the OLTP slide). Three: cheap storage and capable analytical engines made it practical to transform where the data already lives, in SQL that analysts can read and test. ETL still fits when sensitive fields must be masked or dropped before they land (PDPL), when destination compute is scarce or expensive, or when the processing is not SQL-shaped, such as images.

Lake: storage organised as folders of files. Keep every source now in raw/, shape it later in clean/.
The warehouse keeps serving reporting; it still does that job well. The lake is a separate system, not part of the warehouse. Read the folder paths aloud: a lake is folders of files, like a shared drive. Every source lands in raw/ as received: exports of the order tables (CSV), courier events (JSON), support photos. Structured, semi-structured and unstructured data sit side by side. Cleaned copies are written later to clean/, one folder per dataset, often split into several files (part-1, part-2). In the cloud the lake is object storage such as Amazon S3, Azure Data Lake Storage or Google Cloud Storage, where paths act as folders; in the labs it is a folder on the laptop. Do not name file formats yet: Parquet arrives in D1_2. A common pattern then copies curated lake data into the warehouse; the next slide shows that cost. SQL engines and Python process the files. A lake may have well-governed curated datasets. Retaining evidence preserves options, subject to access and retention policies.

The gap: a folder cannot switch all its files at once, so a read during a rewrite gets a mix that was never a real version.
This is the same moment, 10:02. The read and the write overlap: the data scientist gets part-1 new and part-2 old, a combination that was never a whole version of the data. No error is raised, so nobody notices; the model is trained on it. Point at the two ends of the timeline: a read before 10:00 gets all old files and a read after 10:04 gets all new ones, both consistent. Only the overlap fails, and the longer the job and the more frequent the readers, the likelier it is. As before, dashboards still read the warehouse, and the lake’s readers are the data scientists. The same gap would hit any reader of these files, including the job that copies clean lake data into the warehouse. This is a deliberately unsafe multi-file update. Atomic individual writes and strongly consistent object storage do not themselves define a multi-file table transaction. Ask whether a bigger server changes that guarantee.

Engines

DuckDB · Polars · Spark

Separate storage from compute: pick the engine for the workload.
The engines are drawn outside the lakehouse on purpose: they hold no data. Files and Iceberg tables stay in storage; an engine reads them, computes, and writes the result back as new table versions. Compare the warehouse slides, where DuckDB was storage and engine in one box: that bundling is what a warehouse is. Here the same DuckDB appears only as an engine. The arrows point at the transformations, but engines also answer queries, for example DuckDB reading gold for an analyst. DuckDB is a SQL engine and Polars a DataFrame engine, both on one machine. Spark distributes one job across many workers when a single machine is not enough; the course runs it locally, so the lab studies partitions, joins and skew rather than a real cluster. They overlap in capability; choose according to workload and operating needs. In the labs Polars cleans the courier events into silver Parquet (Lab 2.1), DuckDB and Polars read the Iceberg table (Lab 3.1), and Spark reads and writes Parquet (Lab 3.2). Parquet is a file format, not an engine.

08 / The Qafila platform

What the earlier slides left out

Faded: tools you met so far. Highlighted: what each later session adds. CDC + MERGE apply only the changed rows · Semantic layer one definition per metric · Streaming process events as they arrive · Embeddings vectors for AI search · Pandera check DataFrame rows · Contracts agreed schema + expectations

Still to come: each highlighted tool has its own session, and that session opens on this map.
Read only the highlighted cells, one sentence each. CDC + MERGE (D1_4): instead of reloading whole tables, capture the rows that changed in the source and merge them into the target. Streaming (D3_3): process events continuously as they arrive instead of in scheduled batches. Pandera (D2_4): check DataFrame rows against a declared schema before publishing; Lab 2.4 validates supplier price files, and the pipeline stops or sets aside the rows that fail. dbt tests do the same job for warehouse models. Contracts (D4_2): an agreement with the producing team on schema and expectations, checked automatically. Semantic layer (D4_4): define each metric, such as revenue, once, so dashboards and AI answers agree. Embeddings (D4_4): turn text into vectors so an AI assistant can search by meaning. Observe (D4_2): watch freshness, volume, schema, distribution and lineage to catch problems before users do. Govern (D4_3): apply PDPL, masking and access rules across every path.
