Window functions

You want the newest row per customer. Which window function does it, keeping number 1?

rank() OVER (ORDER BY updated_at)
row_number() OVER (PARTITION BY customer_id ORDER BY updated_at)
sum(1) OVER (PARTITION BY customer_id)

Retry what can get better

def get_with_retry(url, params, tries=6):
    for attempt in range(tries):
        r = requests.get(url, params=params, timeout=10)
        if r.status_code == 429:
            wait = float(r.headers.get("Retry-After", 2 ** attempt))
            time.sleep(wait)
            continue
        r.raise_for_status()
        return r.json()
    raise RuntimeError(f"gave up after {tries} tries")

Your first exercise that real pipelines depend on.

Retry

429 and 5xx: "not now", or the server's fault

Don't retry

400 and 404: the same request fails the same way

What goes wrong. A retry with no limit hides a real outage. Give up after a few tries, and let the failure be seen.
This is the exercise in task 3. The three lines inside the if are the student's. 2 ** attempt gives 1, 2, 4, 8 if the server sends no header. Common failure: forgetting continue, so the code falls through to raise_for_status and crashes anyway.

The whole pipeline

A resource is a generator that yields rows, with load instructions on its decorator. A pipeline says where they go.

client = RESTClient(base_url=BASE, data_selector="data",
    paginator=JSONLinkPaginator(next_url_path="next"))

@dlt.resource(name="payments", primary_key="payment_id",
              write_disposition="merge")
def payments(updated_at=dlt.sources.incremental(
        "updated_at", initial_value="2026-08-01T00:00:00.000Z")):
    yield from client.paginate("/payments",
        params={"updated_since": updated_at.last_value})

pipe = dlt.pipeline(pipeline_name="qafila_ingest",
    destination=dlt.destinations.duckdb(str(LAKE_DB)),
    dataset_name="raw")
pipe.run(payments())

One run, three steps

pipe.run extracts, normalizes, then loads. Every step leaves files on disk.

extract

rows to files, in a new load package

normalize

infers the schema, picks the types

load

creates tables, merges rows, saves the cursor

The load fails? The package stays on disk, and the next run finishes it without calling the API again.

Load package. One run's rows as files. It separates a slow source from a destination that may fail.
Extract can be slow: an API. Load can fail: a full disk. Because every package is files, a failed load is retried from the files, not from the source. You don't need to memorise the folder layout. Want more? tools/dlt.ipynb runs the steps one at a time.

Change data capture (CDC): learning every change a source makes. Reading the database's own log is the complete way.
A build, one way per click. Snapshot compare: heavy, and it sees only the net change per night; the 17:15 version never shows up. Query on updated_at: what dlt's cursor did in Lab 2.2.
