08 / Inside a Parquet file

A big file is cut into row groups

Six of the 13 columns of Lab 1.2's file, each drawn as one strip of 3,450,900 values.

A whole column as one piece is too big to write or read at once. One strip per column: the writer would hold all 3.45 M rows before writing a byte, and a reader could only take a whole column.

Row group

a slice of 100,352 rows. The writer fills one, writes each column's piece of it, then starts the next: 35 in this file.

Column chunk

one column of one row group (shaded), compressed on its own. A query reads only the chunks it needs.

Row group: a slice of rows. Column chunk: one column inside it. Still columns, in pieces.
Build this slide in two presses. First the strips: the same columns as the last slide, now for all 3,450,900 lines. Ask the room: if each column were one piece, what would the writer have to keep in memory before it could write the first strip? Everything. And a reader that wants one day would have to take a whole column. Then the cuts: each strip is cut at the same rows. Row group 0 is rows 1 to 100,352 of every column, and so on; the last one holds the 38,932 left over. On disk the file is row group 0's chunks, then row group 1's. Inside a row group the columns stay apart, so part 1 still holds. Row groups are also the unit an engine reads in parallel and the unit it can skip. Lab 1.2 task 3 sets 100,000 rows per group (DuckDB rounds to 100,352); task 2's file uses DuckDB's default of 122,880, so it has 29. Spark aims at about 128 MB per group. Ask: what would an engine need to know to skip a row group without opening it?

Partition: a folder per value. Engines skip folders only when you filter on the partition column itself.
Lab 1.2 task 4 and the stretch. order_date is a new column, created_at cast to a date, and it lives in the folder name (Hive-style: order_date=2026-09-23), not inside the file. 14 / Recall

Part 2: answer before you look

Five questions on Lab 1.2's file. Each key press shows an answer.

  1. Why is the Parquet file 7.8× smaller than the CSV, with the same rows?
    Columns compress: repeats sit together and get a dictionary; values are binary and typed, not text.
  2. Why does a Parquet file have row groups, if it stores columns?
    A whole column is too big to write or read at once. Each row group holds every column for a slice of rows.
  3. A one-day query reads all 35 row groups. What do you change?
    Sort by created_at when writing: then 2 of 35 are read, chosen by the footer's min and max.
  4. The table is partitioned by order_date, yet a one-day query opens 61 files. Why?
    The filter is on created_at, not order_date. Filter on the partition column.
  5. Why not partition by date and store?
    732 tiny files: a full scan is several times slower. Partition by date; let statistics handle the store.
