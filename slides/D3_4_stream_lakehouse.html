Batch 177 becomes snapshot 177 of the table: the same idea as every write in D3_1.

One batch = one commit = one snapshot.
Readers see all 12 rows of 177, or none of them.
Every micro-batch is an atomic commit: a new snapshot that holds the whole batch.
Recall D3_1: every write to an Iceberg table adds files and atomically switches the table to a new snapshot. A reader that runs during the commit sees snapshot 176 or snapshot 177, never half of batch 177. Over the 4 days the job makes 179 commits: 179 snapshots. The snapshot numbers on the slide are positions in the table's history; Iceberg's own snapshot ids are long random numbers.

03 / Where did it stop?

The job must remember where it stopped

The offset from D3_3: the next position in the log to read. A first design saves it in a file after each commit.

Offset: the job's place in the log. After batch 177 (offsets 13488–13499), the next offset is 13500.
This is the naive sink of Demo 3.4 section 2. After each batch the job does two writes: first the data (a commit to Iceberg), then the progress (offset 13500 into checkpoint.json). On restart it reads the file and continues from there. Before batch 177 the file said 13488. Each write is correct on its own. Ask the room what could go wrong.

03 / Where did it stop?

It crashes between step 1 and step 2. Where does it restart?

Batch 177 is in the table. checkpoint.json still says 13488. Predict first: which number does the restart read?

At 13488: batch 177 is appended a second time
Iceberg rolls the commit back, so nothing repeats
At 13500: the table already has batch 177
Yes. The file still says 13488, so batch 177 is read and appended again. C would need the job to look at the table, which this design does not do. B: the commit had finished, and Iceberg never undoes a finished commit. A restart trusts the saved offset, whatever the table already holds.
Allow 45 seconds and let learners commit. A is right: the job reads 13488 from the file and processes batch 177 again; the table has no idea it is the same batch, so it appends it as a new snapshot. B is the common misconception: the commit had finished, and Iceberg never undoes a finished commit. C would need the job to look at the table, which this design doesn't do. 04 / The fix

Put the offset inside the commit

An Iceberg snapshot carries a summary of free-form properties. One commit can hold the data and the progress.

Two writes · a gap between them

1 · commit to the tablesnapshot 177 · 12 rows

a crash here

2 · write checkpoint.jsonoffset 13500
The data is saved, the offset isn't: the batch is replayed.

One commit · no gap

snapshot 177 · one commit
in the commitvalue
12 data rowsKhalid's 4 events + 8 others
qafila.offset13500
qafila.batch_end2026-09-27T23:00:00+00:00
Both are saved, or neither is.
tbl.append(rows, snapshot_properties={"qafila.offset": "13500"})
Exactly once into a table: commit the data and the offset together, in one atomic commit.
Wrong and right on one slide. The left is the naive job. The right is what Lab 3.4 task 1 builds: append the batch with snapshot_properties, so the offset (and the batch's end time, 23:00 UTC = 02:00 Riyadh) are part of snapshot 177's summary. A commit is atomic, so there is no moment where the data exists without the offset. Spark does the same with its checkpoint folder tied to the Iceberg or Delta commit id; Flink uses a two-phase commit. Different code, same idea.

04 / The fix

On restart, ask the table

Lab 3.4 kills the job after 40 batches. The restart reads the offset from the newest snapshot that has one.

snapshot 40 · killedbatch ending 01:00 · 25 Sep3693
restartnewest snapshot with an offset3693
snapshots 41 … 179the other 139 batches
def committed_offset(tbl):
    for snap in reversed(tbl.snapshots()):
        off = snap.summary.additional_properties.get("qafila.offset")
        if off is not None: return int(off)
    return 0
0
batches written twice
0

Compaction commits (later today) carry no offset: skip them.
The table is the checkpoint. Whatever the table holds, it also knows how far it got.
Lab 3.4 task 2: the job is killed after its 40th batch, the one that ended at 01:00 on 25 September; snapshot 40 says offset 3693. The restart walks the snapshots backwards, finds 3693 and continues with batch 41: nothing written twice, nothing skipped. The loop skips snapshots without an offset because maintenance commits, like the compaction later in this session, don't carry one.

A real repeat from batch 176: courier CR-DAM-015's phone sent picked_up for order 5043638 (Dammam) at 01:07:34 and again at 01:08:34 with the same event_id. Batch 177's file is the 43rd of the 45 on 27 September: Khalid's batch, 12 rows, 3.6 kB.

Engines like files of 100 MB or more. Every file costs an open, a footer read and a storage request.
The small-files problem: thousands of tiny files make every read slow. A stream creates it by design.
Lab 3.4 task 3, before compaction: 179 data files, one per batch, 4.9 kB on average, 873 kB in all. Each row of the table is one day folder; in the 27 September row the highlighted file is snapshot 177's, Khalid's 12-row batch in 3.6 kB. The day folders are UTC days, so Khalid's events (01:36 Riyadh on 28 September) sit in event_day=2026-09-27. Each file means another object to open and another footer to read (Parquet, D1_2), and on object storage every request is billed. Shorter batches make it worse: fresher data, more files. At Qafila's real scale, a 1-minute trigger would write 1,440 files a day per partition touched.

Compaction: rewrite many small files into a few large ones. The data doesn't change; reads get much faster.
Lab 3.4 task 3: for each day, scan its rows, sort by event time and overwrite the day with one file. Each day's many small files become one file holding the same rows. 179 files become 4, the average file grows from 4.9 kB to 76 kB, and a full scan on a laptop goes from about 0.5 s to 0.02 s (your timings will differ; the ratio is what matters). The row count is checked to be identical. Compaction is a commit too: a new snapshot with fewer, bigger files. In production nobody hand-rolls this: Spark's rewrite_data_files procedure, or a managed service, does it on a schedule.

05 / Housekeeping

Three chores keep a streaming table healthy

Run them on cold partitions (yesterday's), so they don't race the stream job.

Compact

rewrite small files into large ones

rewrite_data_files

Expire snapshots

drop old snapshots: 48 new ones a day

expire_snapshots

Remove orphan files

delete files that no snapshot points to

remove_orphan_files
Compaction and the stream job both commit. If they touch the same day at the same moment, one of them retries.
S3 Tables, Databricks and Snowflake run these for you.
Maintenance: compact, expire snapshots, remove orphan files. Otherwise reads slow down and storage only grows.
One 30-minute stream makes 48 snapshots a day; after a month, time travel reaches back through 1,440 of them and every old file is still on disk. Expiring snapshots (D3_1's stretch task) drops old versions; removing orphan files deletes data files that no snapshot references any more, such as leftovers of failed writes and expired snapshots. Each chore is itself a commit, so it can conflict with the stream job: Iceberg's optimistic concurrency makes the loser retry, and scheduling the chores on yesterday's partitions avoids most conflicts.

The table is a stream too

The silver job remembers the last snapshot it read, like a consumer offset, and asks only for what was added since.

    from_snapshot_id_exclusive=last_seen)

Silver job

reads only the rows added after 187

2,962 rows written · 2,962 read

Incremental read: the rows appended since a given snapshot. Jobs chain through tables instead of rescanning them.
Lab 3.4 task 5. Iceberg records what each snapshot appended, so a downstream job keeps its own "offset": the last snapshot it processed. After the compaction the table is at snapshot 187; the stream runs one more day (43 batches, snapshots 188 to 230, 2,962 new rows), and the incremental read returns exactly those 2,962 rows. Compaction snapshots add no new rows, so incremental appends skip them. This is how Flink and Spark stream from Iceberg tables, and how dbt incremental models avoid full rebuilds.

09 / Architectures

Lambda: two paths for one number

A fast path for now, a nightly batch for the truth. Queries merge the two.

LogKafka, kept for days
→
Speed jobstream: fast, approximate
Batch jobnightly: slow, exact
→
Merged viewtoday from speed, older days from batch
→
Operationsreads the merged view
Every metric is written twice. Fix a bug in one path, and the other still has it.
Lambda: a speed layer and a batch layer, merged at query time. Two code paths that drift apart.
The classic answer from the 2010s, when streams were thought to be approximate. The batch layer recomputes the truth every night from the stored events; the speed layer covers the hours since; queries merge the two. It works, but every metric exists twice, often in two languages (a Flink job and a SQL model), and the two drift: the live delivery count and the nightly count disagree, and nobody knows which to trust.

Kappa: one streaming path. A bug fix or a new metric means replaying the retained log through the new job.
Demo 3.4 section 6 does exactly this: the naive table (with a replayed batch and the phones' repeats) is not patched; the fixed logic replays the retained log from offset 0 into a new table, and readers switch to it. The catch: the log must be kept long enough (Kafka retention or tiered storage) and the output must be replaceable.
