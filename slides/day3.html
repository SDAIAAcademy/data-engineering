Review: cursors and idempotency

Your paged load crashes halfway, and you rerun it from the last saved cursor. Some rows come in a second time. What keeps the table right?

Run it only at night, when nothing else is writing
Delete the table and do a full load after every crash
A small overlap on the cursor, plus an upsert on the primary key
Save the cursor before writing the page, never after
Why. An idempotent load: running it twice gives the same table. Upserting on the key makes repeats harmless, so a retry is safe. Saving the cursor first is what loses rows.
Review of Lab 2.1 and Lab 2.2. Answer C. In the Day 2 run, a rerun of the merge load stayed at 29,526 rows. Saving the cursor before writing means a crash skips those rows for good.

Review: CDC and MERGE

A customer changes city twice in one evening, and the two CDC events reach you in the wrong order. What do you do before the MERGE?

Keep the latest change per customer, ordered by the log position (lsn)
Keep the event that arrived last
Apply both in arrival order, since MERGE sorts them out
Throw both away and copy the whole table again
Why. Arrival order isn't change order. Sort by lsn and keep one row per key, and MERGE then applies each customer's true last state. Updates, inserts and deletes all go through the same statement.
Review of Lab 2.3. Answer A. CDC: change data capture, the feed of every change from the app's database. Customer 100898 from yesterday ended in the wrong city when events were applied in arrival order.

A model is one SELECT

dbt writes the CREATE for you. You keep the only part that matters, and say what it reads.

CREATE OR REPLACE TABLE order_sales AS
SELECT o.order_id, o.store_id, o.status,
       i.quantity * i.unit_price
         - i.discount AS net_amount
FROM raw.order_items i
JOIN orders_clean o
  ON i.order_id = o.order_id

SELECT o.order_id, o.store_id, o.status,
       i.quantity * i.unit_price
         - i.discount AS net_amount
FROM {{ source('raw', 'order_items') }} i
JOIN {{ ref('orders_clean') }} o
  ON i.order_id = o.order_id
Takeaway. Model: one .sql file with one SELECT. {{ ... }} is Jinja: dbt fills it in before the SQL runs.
The file name becomes the table name. Show the two side by side and let them spot the differences: no CREATE, and two names replaced. dbt is the same SQL you already know, plus a little templating. In Lab 3.2 you'll see the compiled SQL with the names filled in.

A dbt test is a query that looks for bad rows

- name: stg_orders
  columns:

    - name: store_id

        - relationships:
            arguments:
              to: ref('stg_stores')
              field: store_id

Assets: the tables you want, not the steps

Say what each table is built from. Dagster works out what to run, in what order.

raw/delivery_eventsbuilt by a Python function
raw/reviewsanother asset, with nothing downstream yet
ops/delivery_eventsdeps: raw/delivery_events
ops/delivered_per_storedeps: ops/delivery_events

Task-based tools ask: which step next? Asset-based ones ask: is this table up to date?

Takeaway. Asset: a table or file you want to exist, plus the function that builds it. Materialize: build it now.
The word software-defined asset appears in Dagster's documents; it means this. Because each asset names what it's built from, the graph draws itself, and you can ask for one table and everything downstream of it. Everything in the lab runs in the notebook with dg.materialize, no server needed. dagster dev gives you the web interface; the capstone kit has one.

An asset is a decorated function

@dg.asset(key=["ops", "delivered_per_store"], deps=[ops_delivery_events])
def ops_delivered_per_store():
    sql("""CREATE OR REPLACE TABLE ops.delivered_per_store AS
           SELECT store_id, count(*) AS delivered
           FROM ops.delivery_events
           WHERE event_type = 'delivered' GROUP BY ALL""")

result = dg.materialize([ops_delivery_events, ops_delivered_per_store])
Takeaway. A decorator (@) labels the function. key names the table, deps names its parents: that's the whole graph.
Read from the top. Python basics are enough: a decorator is a function that wraps your function, and here it just registers it. The body is plain SQL through a small helper. Nothing runs until materialize.
