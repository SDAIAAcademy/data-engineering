An assistant could answer it. With which numbers?
Ask your data: the question is easy to write. The answer depends on definitions the model doesn’t have.

Which basket?

items only, or with the 9 SAR delivery fee?

Which orders?

delivered only, or cancelled too?

Which day?

23 September in Riyadh time, or in UTC?

Each guess changes the number. None raises an error: it answers confidently, and differently each time.
A build in two steps. The question is Lab 4.4’s: the average basket in Jeddah on Saudi National Day, 23 September. Assistants that “ask your data” are everywhere now: Snowflake Cortex Analyst, Databricks Genie, BI copilots, internal agents. Ask the room: if a model wrote SQL against our raw tables for this question, what would it have to guess? Press: three guesses hide in one sentence. Basket: items_amount, or order_total with the fee. Orders: delivered only, or every status. Day: the app stores UTC, but Qafila’s day is Riyadh time (D2_1 converted it). Finance answered all three on Day 2: revenue is delivered items, without delivery fees, by Riyadh date. A model writing SQL on raw tables answers confidently, and differently each time it guesses. A human analyst learns the definitions in their first week; a model has to be given them.

02 / Semantic layer

Metrics defined once, in a file

Lab 4.4’s semantic layer, shortened: 6 metrics and 6 dimensions over the Day 2 star schema.

model: orders
from: marts.fct_orders AS o
joins:
  - marts.dim_stores AS s USING (store_id)
dimensions:
  city:  {expr: s.city}
  month: {expr: "date_trunc('month', o.order_date)::DATE"}
metrics:
  revenue_sar:
    expr: "round(sum(o.items_amount)
           FILTER (WHERE o.status = 'delivered'), 2)"
    description: Revenue, sales, money made from delivered
      orders in SAR, excluding delivery fees.
  avg_basket_sar:
    expr: "round(avg(o.items_amount) FILTER (…), 2)"
  • from, joins · which table, which joins
  • dimensions · what people group and filter by
  • expr · each metric: its SQL, once
  • description · and its words, for people and models
Semantic layer: business definitions (metrics, dimensions, joins) stored once and compiled to SQL.
The real file from Lab 4.4 task 1, shortened. The from and joins say where the data lives; dimensions are what people group and filter by (order_date, month, city, store_id, payment_method, promo_code); metrics are expressions with a description in English and Arabic (orders, delivered_orders, revenue_sar, avg_basket_sar, sla_rate, refund_rate). revenue_sar is Finance’s D2_2 definition, written down. The same idea at scale: the dbt Semantic Layer with MetricFlow, Cube, LookML, Snowflake semantic views.

02 / Compile

Ask for metrics by dimensions; the layer writes the SQL

A semantic query names what it wants. compile_query turns it into SQL and a list of parameters.

{"metrics":    ["revenue_sar"],
 "dimensions": ["city"],
 "filters":    [["month", "=", "2026-09-01"]]}

a semantic query: data, not SQL · ↓ compile_query

SELECT s.city AS city,
  round(sum(o.items_amount) FILTER (WHERE o.status = 'delivered'), 2) AS revenue_sar
FROM marts.fct_orders AS o
JOIN marts.dim_stores AS s USING (store_id)
WHERE date_trunc('month', o.order_date)::DATE = ?
GROUP BY ALL
ORDER BY city
-- params: ['2026-09-01']
result · September
cityrevenue_sar
Dammam600,239.76
Jeddah1,062,633.91
Riyadh1,748,564.50
Semantic query: metrics, dimensions and filters as data. Compiling it is mechanical, and testable.
Lab 4.4’s compile_query, run on its example: select the dimension and metric expressions, add the from and the joins, turn each filter into the dimension’s expression and a question mark, group and order by the dimensions. The value 2026-09-01 never enters the SQL text: it travels in params. The result is the lab’s output; Riyadh is the first row of the previous chapter’s table, by construction.

By construction: one definition gives one number; parameters keep values out of the SQL. The assistant and the dashboard now share one definition, and one way in.
The lab’s two checks. First, the semantic layer’s revenue_sar and sla_rate by order_date and city match marts.mart_daily_city_sales row for row: the dashboard and the layer agree. When Finance changes the definition (say, to include fees), it changes in one place.

03 / The pipeline

An embedding pipeline is a data pipeline

Rows in, text built, vectors stored next to the model that made them.

raw.products347 active products
→
textboth names · category · description
→
product_vectorsproduct_id · vec FLOAT[256]
model: potion-multilingual-128M
  • A description changes · re-embed that row: change data capture, as in D1_4
  • A new model · re-embed everything; never compare vectors from two models
  • Millions of rows · add an index: DuckDB vss (HNSW), pgvector, LanceDB, Qdrant
Keep vectors in sync with their source rows, and version the model next to them.
The vectors are a derived table like any mart: they go stale when the source changes. Re-embed changed rows on each run (the same incremental logic as D1_4 and D2_3), store the model name beside each vector, and treat a model change as a full rebuild. At 347 products a full scan is instant; at catalog scale an approximate index (HNSW in DuckDB’s vss extension, pgvector in Postgres) keeps search fast.

05 / Guardrail

Validate every plan before it touches data

Lab 4.4’s validate() on four bad plans: whatever wrote them, a model or a person.

validate(plan) · Lab 4.4
planblocked: whywhat it was
dimensions: ["national_id"]unknown dimension ‘national_id’D4_3: Secret, never a dimension
filters: [["city", "; DROP", "x"]]operator ‘; DROP’ not allowedan injection attempt
metrics: ["salary"]unknown metric ‘salary’not in the layer: no guessing
metrics: []ask for 1 to 3 metricsan empty or greedy plan
4 of 4
blocked before the database
Allow-lists: known metrics and dimensions, allowed operators, 1–3 metrics, a limit of at most 1,000.
Guardrail: an allow-list check on the plan. Personal data can’t be asked for, because it was never a name.
The lab’s four bad plans, all rejected with a ValueError. national_id isn’t a dimension because D4_3 classified it Secret and the gold layer never carried it: the safest column is one the assistant can’t name. The operator check blocks injection through the plan itself; the metric check stops the model inventing salary; the count check stops empty and greedy plans. Role-based access belongs underneath too: the assistant should query as the user, through D4_3’s views.
